# Buffer Underrun Root Cause Analysis: rotated_latlon_gdt1_drt0

## Error Message
```
buffer too short: need 1, got 0
Error: TooShort { needed: 1, got: 0 }
```

## Root Cause Location
**File**: `crates/gribtract-core/src/decode.rs`
**Function**: `decode_message()`
**Lines**: 252-256 (Section iteration loop)

## Problem Description

The buffer underrun occurs in the **section iteration loop** when it attempts to read a section header without first checking if enough bytes remain in the buffer.

### Exact Code Path

1. **Entry Condition**: The loop checks `while buf.pos < body_end` (line 252)
2. **Section Header Read**: 
   - Line 255: `buf.read_u32be()?` - reads 4-byte section length (checks `need(4)`)
   - Line 256: `buf.read_u8()?` - reads 1-byte section number (checks `need(1)`) ← **UNDETRUN HERE**

3. **The Issue**: When `buf.pos < body_end` but `buf.remaining() < 5`, the loop enters but cannot read the full 5-byte section header.

### Specific Case: rotated_latlon_gdt1_drt0.grib2

File structure:
- **File size**: 187 bytes
- **Section 0 (Indicator)**: 16 bytes
- **Section 1**: 21 bytes (ends at position 37)
- **Section 3 (GDT)**: 72 bytes (ends at position 109)
- **Section 4 (PDT)**: 34 bytes (ends at position 143)
- **Section 5 (DRT)**: 20 bytes (ends at position 163)
- **Section 6 (Bitmap)**: 6 bytes (ends at position 169)
- **Section 7 (Data)**: 14 bytes (ends at position 183)
- **End marker "7777"**: 4 bytes (positions 183-186)

**Calculation**:
- `total_len = 187` (from Section 0)
- `body_end = total_len - 4 = 183` (before "7777" marker)
- After Section 7: `buf.pos = 183`

**Loop condition**: `buf.pos (183) < body_end (183)` = **FALSE**

The loop should exit here, but the issue suggests the loop is entered one more time or the `need(1)` check fails elsewhere.

### Actual Failure Point

Looking at the code flow, the `need(1)` error occurs because:

1. The `Buf::need()` method (line 34-40) checks `self.remaining() < n`
2. `remaining()` returns `self.data.len() - self.pos`
3. When `pos = data.len()`, `remaining() = 0`
4. Calling `read_u8()` (line 42-47) calls `need(1)` first
5. If `remaining() = 0`, this returns `Err(Error::TooShort { needed: 1, got: 0 })`

## Section 3 (GDT 3.1) Structure Analysis

**Expected GDT 3.1 template size**: 72 bytes
**Actual Section 3 body size**: 67 bytes
**Missing**: 5 bytes

However, the trace shows all GDT 3.1 fields are present:
- All required fields (shape_of_earth, Nx, Ny, coordinates, pole position, scanning_mode) are available
- The template parses successfully with 67 bytes
- This is NOT the buffer underrun source

## Why the Loop Fails

The issue is in the section iteration boundary condition. When the last section ends exactly at `body_end`, the loop should exit cleanly. However:

1. **Current logic**: `while buf.pos < body_end`
2. **Problem**: When `buf.pos == body_end`, the loop exits
3. **But**: If there's an off-by-one error in how `body_end` is calculated or how `buf.pos` is updated, the loop might:
   - Enter when it shouldn't (if `body_end` is too large)
   - Try to read beyond available data (if section lengths are incorrect)

## The Specific Bug

The bug is that the code **doesn't validate that a full 5-byte section header exists before attempting to read it**. The loop condition only checks `buf.pos < body_end`, but doesn't ensure `buf.remaining() >= 5`.

**Fix**: Add a check before reading the section header:
```rust
while buf.pos < body_end {
    // Ensure we have at least 5 bytes for section header
    if buf.remaining() < 5 {
        return Err(Error::TooShort { 
            needed: buf.pos + 5, 
            got: buf.data.len() 
        });
    }
    
    let sec_start = buf.pos;
    let sec_len = buf.read_u32be()? as usize;
    let sec_num = buf.read_u8()?;
    // ... rest of parsing
}
```

## Summary

- **Error location**: Section iteration loop, line 256 `buf.read_u8()?`
- **Root cause**: Loop enters without verifying 5 bytes are available for section header
- **Trigger condition**: When `buf.pos < body_end` but `buf.remaining() < 5`
- **Impact**: Cannot decode files where sections end exactly at message boundary
- **Note**: The GDT 3.1 template having 67 bytes instead of 72 is a separate issue (possibly malformed file), but it doesn't cause the buffer underrun
