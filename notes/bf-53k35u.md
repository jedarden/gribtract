# BF-53k35u: should_reprobe Integration Verification

## Task
Verify that the `should_reprobe` function is properly integrated into all provider-selection code paths.

## Findings

### Primary Entry Point Analysis

**Both `is_valid` implementations DO call `should_reprobe`:**

1. **gribtract/src/provider_probe.rs:184** ✓
   - Method: `ProviderProbe::is_valid(max_age_secs, tracker)`
   - Delegates to: `tracker.should_reprobe(provider)`
   - Line 193: `if tracker.should_reprobe(provider) { return false; }`

2. **gribtract-fetch/src/probe.rs:361** ✓ (NOT a bug)
   - Method: `ProviderProbe::is_valid(results, max_age)`
   - Delegates to: `self.should_reprobe(provider)`
   - Line 370: `if self.should_reprobe(provider) { return false; }`

**The task description's claim that gribtract-fetch "manually checks threshold instead of calling should_reprobe" was INCORRECT.**

### Architectural Separation (Not Duplication)

These are **two distinct `ProviderProbe` structs** serving different purposes:

| Aspect | `gribtract::ProviderProbe` | `gribtract_fetch::probe::ProviderProbe` |
|--------|----------------------------|----------------------------------------|
| **Purpose** | Read cached `provider-probe.json` | Actively run probe tests against providers |
| **Use case** | Runtime consumption of probe results | Generating new probe results (xtask) |
| **State** | Immutable after loading | Mutable (holds failure counters) |
| **Failure tracking** | External `ProviderFailureTracker` | Built-in `consecutive_failures` field |
| **Feature gate** | `#[cfg(feature = "provider-probe")]` | Always available |

This is **intentional separation of concerns**, not a bug to fix.

✓ Code compiles without errors
✓ All `is_valid` unit tests pass:
  - `test provider_probe::tests::is_valid_with_consecutive_failures_returns_false ... ok`
  - `test provider_probe::tests::is_valid_with_fresh_probe_and_no_failures ... ok`

  - `test provider_probe::tests::is_valid_with_stale_probe_returns_false ... ok`

## Conclusion

**No fix needed.** The `should_reprobe` integration is complete and working correctly. Both code paths properly delegate to the `should_reprobe` function for determining when providers need re-probing due to consecutive HTTP failures.
